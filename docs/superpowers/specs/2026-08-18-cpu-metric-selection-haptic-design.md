# CPU 指标选择触感设计

## 目标

用户点击主机详情页 CPU 指标格、切换该指标在趋势图中的显示状态时，每次点击都立即产生一次 App 统一的高强度触感。选中与取消选中使用相同反馈。

## 现状与问题

页面当前把 `sensoryFeedback` 直接绑定到 `cpuVisibility`，且修饰符位于会跟随指标内容和图表状态重建的 CPU 网格子树。虽然可见集合会变化，但触感生命周期与业务状态耦合，页面重建时可能重新建立触发基线，反馈不够可靠。

## 方案比较

1. 在按钮动作中直接调用 UIKit feedback generator。触发最直接，但把 UIKit 命令式调用带入 SwiftUI 页面，且不符合项目中普通 SwiftUI 控件的统一模式。
2. 继续以 `cpuVisibility` 为触发值，只把修饰符移到页面根层。改动小，但触感仍依赖业务状态值，后续若出现“点击但状态未变化”的交互就不会反馈。
3. 使用独立点击计数器作为 `sensoryFeedback` 触发值，并把修饰符放在稳定页面层。每次有效按钮点击递增一次，业务状态与触感事件解耦；与终端快捷键栏现有实现一致。

采用方案 3。

## 交互与数据流

1. 用户点击任一 CPU 指标格。
2. 页面切换 `CPUChartVisibility` 中对应指标的可见状态。
3. 页面递增 CPU 指标触感计数器。
4. 稳定页面层上的 `sensoryFeedback` 观察到计数器变化，触发 `ConnHapticFeedback.highImpact`。

不新增动画、Toast 或设置项；不改变 CPU 指标数据、图表绘制和无障碍文案。

## 验证

- 源码契约测试确认 CPU 指标点击会递增独立触感计数器。
- 源码契约测试确认高强度触感绑定在稳定页面层，CPU 网格不再直接以 `cpuVisibility` 作为触发值。
- `HostOverviewChartUITests` 连续点击同一 CPU 指标两次，验证可见状态按
  `visible → hidden → visible` 变化且 App 进程稳定。模拟器无法观测物理震动，UI 测试只验证触发事件对应的交互边界。
- iOS 测试目标必须编译通过；若存在用户已经启动的模拟器，单元测试和 UI 测试都只在该设备执行。没有已启动设备时不自行启动，并明确报告测试仅完成编译。
- 物理触感的强度和每次点击一次反馈需要在真机人工验收。
