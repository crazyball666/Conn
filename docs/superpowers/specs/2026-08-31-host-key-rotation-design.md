# 主机指纹变更确认与重连设计

## 背景与目标

VPS 重装系统后，SSH 服务会生成新的主机密钥。Conn 当前采用 TOFU（首次连接记录，之后严格比对）：检测到指纹变化时必须阻断连接，但服务器列表目前只保留普通错误文案，用户无法在确认来源后完成恢复。

本次只解决“用户确认服务器已重装/密钥已轮换后的安全恢复”这条路径，不降低默认校验强度，也不影响终端、文件管理、Docker 和其他连接调用方。

## 安全边界

1. 首次连接仍自动记录指纹。
2. 已记录指纹与当前指纹不一致时，连接仍然失败，不自动覆盖。
3. 列表保留类型化的校验端点、`expected`（已记录）与 `actual`（当前）指纹，并展示现有的风险说明；跳板机场景始终更新实际发生校验的那一跳。
4. 只有用户在确认弹窗中明确选择“更新指纹并重连”后，才允许覆盖；取消或更新失败都继续阻断。
5. 覆盖采用“仅当本地记录仍等于弹窗中的旧指纹”条件，并在监控状态中校验 endpoint/expected/actual 三元组，避免过期弹窗覆盖其他并发更新。
6. 覆盖结果区分成功、旧指纹过期和指纹库不可用。只有成功覆盖后才驱逐该主机的池化会话，再只对该主机发起一次新的 SSH 握手；重连失败不自动重复弹窗或无限重试。

## 用户流程

服务器列表采集到 `hostKeyMismatch` 后：

1. 主机卡片显示离线状态，按卡片顺序排队弹出确认弹窗，包含校验端点、已记录指纹和当前指纹，以及系统重装/中间人风险提示。
2. 用户选择“取消”：保持阻断，卡片仍显示指纹变更错误。
3. 用户选择“更新指纹并重连”：执行条件覆盖、驱逐旧连接并触发该主机单次采集重连。
4. 重连成功后清除错误并恢复卡片指标；失败则保留真实失败原因，不再自动覆盖其他指纹。确认后的重连若观察到第三个指纹，不在同一次操作中再次弹窗；用户重新进入页面或主动刷新后再重新确认。

## 实现边界

- `HostKeyStore` 增加带旧值条件的覆盖操作，结果区分替换成功、条件过期和存储不可用；持久化 GRDB 实现和内存测试实现都复用同一语义。
- `MonitorScheduler` 在原有 `errors` 之外保留指纹变更的结构化状态（含精确 endpoint），并提供绕过普通传输重试的单主机一次重连入口；代次和 in-flight 规则继续阻止旧采集结果写回。
- `AppDependencies` 暴露同一份指纹库给服务器列表 ViewModel，避免另建存储或通过删除主机绕过校验。
- `ServersView` 只负责弹窗与用户动作；覆盖、驱逐、重连由 ViewModel/监控依赖协调。
- 使用 `L()` 新增弹窗标题和操作文案，并补齐 zh-Hans、zh-Hant、en、ja、ko。

## 验证

- ConnSSH 单测覆盖条件覆盖成功、旧值已变化时拒绝覆盖，以及覆盖后 TOFU 匹配；错误携带实际校验 endpoint。
- ConnMonitor/ServersViewModel 单测覆盖指纹错误结构化保留、确认后清除并单次重连、过期 actual、并发采集和共享 endpoint 不被误写。
- 增加服务器列表 XCUITest，验证指纹变更确认入口及取消/确认后的页面稳定性；如当前模拟器本地数据库状态阻止 App 启动，必须在交付中明确记录，不清理用户模拟器数据规避问题。
