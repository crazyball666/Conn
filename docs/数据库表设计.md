# Conn 数据库表设计（现状）

整理日期：2026-07-27
来源：`Packages/ConnPackages/Sources/ConnStore/Migrations/SchemaV1~V3.swift`

引擎 GRDB（SQLite）。库文件 `Application Support/Conn/conn.sqlite`，
`AppDatabase` 构造即执行迁移。DEBUG 构建开启 `eraseDatabaseOnSchemaChange`，
schema 变化自动重建库。`foreignKeysEnabled = true`。

命名遵循技术实现方案 §3：蛇形字段名；实体表带 `uuid TEXT PRIMARY KEY`、
`created_at` / `updated_at`（毫秒时间戳）；为 v1.1 ConnSync 预留
`sync_dirty` 与 `deleted_at`（墓碑）。

当前共 **11 张表**，分三个迁移版本建成。

---

## 迁移版本

| 版本 | 标识 | 内容 |
|---|---|---|
| V1 | `v1_initial_schema` | 9 张表 + 4 个索引 |
| V2 | `v2_snippet_folder` | `snippet_folder`（仅 `name` 主键） |
| V3 | `v3_snippet_multi_folder_and_order` | 给 `snippet_folder` 加 `sort_order`；建 `snippet_folder_membership`；把 `snippet.folder` 单分组数据搬进成员表 |

## 一、实体表（带墓碑，参与 v1.1 同步）

### `host_group` — 主机分组

| 列 | 类型 | 约束 |
|---|---|---|
| `uuid` | TEXT | PRIMARY KEY |
| `name` | TEXT | NOT NULL |
| `sort_order` | INTEGER | NOT NULL DEFAULT 0 |
| `created_at` | INTEGER | NOT NULL |
| `updated_at` | INTEGER | NOT NULL |
| `sync_dirty` | INTEGER | NOT NULL DEFAULT 0 |
| `deleted_at` | INTEGER | 墓碑 |

DAO：`HostGroupStore`。**注意：v1 就建好了，但从未接入任何 UI。**

### `ssh_key` — SSH 密钥

| 列 | 类型 | 约束 |
|---|---|---|

| `kind` | TEXT | NOT NULL |

| `created_at` / `updated_at` / `sync_dirty` / `deleted_at` | INTEGER | 同上 |

DAO：`SSHKeyStore`。红线：私钥密文永不入库。

### `host` — 主机

| 列 | 类型 | 约束 |
|---|---|---|
| `uuid` | TEXT | PRIMARY KEY |
| `name` | TEXT | NOT NULL |
| `address` | TEXT | NOT NULL |

DAO：`SnippetStore`，默认排序 `sort_order ASC, title ASC`。

|---|---|---|

## 四、外键全景

全库只有 4 处外键声明：

| 从 | 到 | onDelete |
|---|---|---|
| `host.key_uuid` | `ssh_key.uuid` | SET NULL |
| `host.group_uuid` | `host_group.uuid` | SET NULL |
| `snippet_folder_membership.snippet_uuid` | `snippet.uuid` | CASCADE |
| `snippet_folder_membership.folder_name` | `snippet_folder.name` | CASCADE |

**关键性质：实体删除是写墓碑（`deleted_at`）而非 DELETE，所以上述
`ON DELETE` 级联在正常业务路径上永远不会触发。** 它们只在物理清理
（墓碑 30 天后清除）时才有意义。

`jump_chain` 是一串没有外键的 `Host.id` JSON 数组——这是本项目对
「多值引用」的既定做法。

## 五、删除语义

### 判据

**这张表的数据会不会跨设备同步？** 会 → 软删除；不会 → 真 DELETE。

软删除唯一的价值是让删除动作能传播到其他设备——没有墓碑，A 设备删掉的记录会被
B 设备当作「本地新增」推回来。不参与同步时它是纯负担：每个查询都必须记得写
`WHERE deleted_at IS NULL`（漏一次就是数据泄漏 bug）、数据永远不真正消失、
还得额外维护清理任务。

PRD §341 定义的同步范围是「主机 / 密钥（加密）/ 片段 / 设置」。

### 现状速查

| 表 | 删除方式 | 是否符合判据 |
|---|---|---|
| `host` / `ssh_key` / `host_group` / `snippet` | 软删除，写 `deleted_at` 墓碑 | ✅ 要同步 |
| `known_host` / `run_history` / `metric_sample` | 真 DELETE | ✅ 不同步 |
| `snippet_folder` / `snippet_folder_membership` | 真 DELETE | ❌ **该同步却在真删** |
| `probe_target` / `app_setting` | — | 无人使用 |

整体划分只错了一处：`snippet_folder`。

## 六、已知问题

1. **`snippet_folder` 破坏同步模型。** 没有墓碑意味着 v1.1 ConnSync 接入后，
   A 设备删除的分组会被 B 设备当作「本地新增」同步回来——`HostStore.softDelete`
   的注释已就同一问题说明过后果。重命名分组同样有损：因为 name 是主键，改名
   等于删旧建新，`sort_order` 会丢失。

2. **两张表建了但从未使用。** `probe_target`、`app_setting` 全仓无 DAO、
   无 SQL 引用。要么在后续版本接上，要么删掉。

3. **`metric_sample` 是纯写入表，没有任何读取方。** `MonitorScheduler` 每次采集
   往里写一行，但 `MetricRepository.latest()` 与 `recentSamples()` 全仓无调用方。
   详情页的趋势图走的是 `HostOverviewViewModel` 的**内存数组**（上限 40 点，
   离开页面即清空），从头到尾不碰 SQLite。也就是说每次采集的落库 + 启动时的
   48h 清理任务全是无用功。
   （附带：它也只持久化 7 项指标，`cpuCores` / `memTotalBytes` / `uptimeSeconds` /
   网络与 IO 速率等运行时字段都不入库。）

4. **只有 `host` 表为 `deleted_at` 建了索引。** `snippet`、`ssh_key`、
   `host_group` 的 `WHERE deleted_at IS NULL` 是全表扫描。当前数据规模下
   无影响，规模上来需要补索引。

5. **`host.group_uuid` 与 `host_group` 表自 v1 起从未接入 UI。**
   单分组外键与整张分组表都是死代码。

6. **`snippet.folder` 是遗留列。** V3 迁移后已无人读写，但列还在。

7. **墓碑清理从未实现。** 技术实现方案 §4.11 写明「墓碑 30 天后物理清除」，
   但全仓没有任何清理 `deleted_at` 的代码——启动时只清理了 metric 的 48h 样本。
   墓碑目前会永久累积。

## 七、本次改动后的形态

见 `docs/superpowers/specs/2026-07-27-server-groups-design.md`。要点：

**迁移**
- 迁移链**折叠回 `SchemaV1`**，删除 `SchemaV2` / `SchemaV3`，不新增版本。
  DEBUG 的 `eraseDatabaseOnSchemaChange` 会自动重建库，现有数据全部清空。

**分组：两侧改为完全对称**

现状的不对称是这次要修的问题本身——主机是单分组外键（且从未接入 UI），
命令是多分组成员表，命名一个叫 `group` 一个叫 `folder`：

| | 现状（主机） | 现状（命令） | 改动后（两侧一致） |
|---|---|---|---|
| 分组定义表 | `host_group`（uuid 主键，含墓碑） | `snippet_folder`（**name 主键，无墓碑**） | `host_group` / `snippet_group`，同构 |
| 归属方式 | `host.group_uuid` 单外键，**只能进一个组** | `snippet_folder_membership` 成员表，可进多个组 | 各自的成员表，都可进多个组 |
| 成员表 | **无** | `snippet_folder_membership(snippet_uuid, folder_name)` | `host_group_membership(host_uuid, group_uuid)`<br>`snippet_group_membership(snippet_uuid, group_uuid)` |
| 命名 | `group` | `folder` | 统一 `group` |
| UI | 从未接入 | 已接入 | 两侧都接入 |

具体动作：
- `host` 删除 `group_uuid` 列与 `idx_host_group` 索引；
  新增 `host_group_membership(host_uuid, group_uuid)`，双列主键，**不声明外键**。
- `snippet` 删除 `folder` 遗留列。
- `snippet_folder` / `snippet_folder_membership` 替换为
  `snippet_group`（与 `host_group` 完全同构，含 uuid、`sort_order`、时间戳、
  `sync_dirty`、`deleted_at`）+ `snippet_group_membership(snippet_uuid, group_uuid)`，
  同样不声明外键。
- 两张成员表结构完全一致，只是外层实体列名不同（`host_uuid` / `snippet_uuid`）。
- 成员行本身是真删除，不需要墓碑：它不是独立同步单元，只随父实体的 `save`
  被整体重写，§4.11 的冲突策略是 record 级 LWW。
- 代价：分组软删除时必须**显式**清成员行，没有级联兜底。

**删表**
- `probe_target`、`app_setting` 删除。全仓无任何代码引用，零风险。
- `metric_sample` 删除，指标不再落库，改为纯内存态。连带删除
  `MetricSample`、`MetricRepository`、`MetricStore`、`MetricRecord`、
  `MetricStoreTests`，以及 `HostMetrics.sample`（其文档注释即写「落库样本」）、
  `MetricCollector` 中构造它的那段、`MonitorScheduler.store` 参数与那个
  detached 写入 Task、`AppDependencies.metricStore` 与启动时的 `pruneSamples`。
  测试中无任何 `MetricSample` 构造点，波及面干净。
  **代价**：PRD §离线「无网时可查看最后一次监控快照」失去地基，该需求放弃；
  历史曲线本就是 PRD 对比矩阵标注的 `v1.5💰` 项，无损失。

**结果**

改动后共 **9 张表**：`host`、`host_group`、`host_group_membership`、`ssh_key`、
`snippet`、`snippet_group`、`snippet_group_membership`、`known_host`、`run_history`。

已知问题第 1、2、3、5、6 条全部消解；第 4（`deleted_at` 索引）与
第 7（墓碑清理未实现）不在本次范围。
